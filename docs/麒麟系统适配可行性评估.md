# TypeBridge 麒麟系统适配可行性评估

评估日期：2026-09-28
评估对象：把 TypeBridge 跨屏输入工具做到银河麒麟（麒麟软件 KylinOS）上运行

---

## 一、结论先行

**技术上可行，但不是"移植"，而是"重写一个 Linux 版"。**

- 整个工具里，真正要重新攻坚的只有**一个模块**，就是"把文字送进光标处"这一步。其余全是体力活。
- 手机端网页那一半**可以 100% 复用**，一行都不用改。
- 最大的不确定因素不在代码，而在目标机器的**显示协议是 X11 还是 Wayland**。这一条直接决定注入方案走哪条路，而且同一个麒麟的不同 SP 版本还会不一样，**必须现场检测，不能拍脑袋**。

预计工作量：最小可用版 1.5 到 2 天，加上托盘和打包 3 天左右。

## 二、现有代码哪些能复用

| 模块 | 能否复用 | 说明 |
| --- | --- | --- |
| 手机端页面（mobile.html / pair.html / 二维码） | ✅ 完全复用 | 纯浏览器技术，跟电脑装什么系统无关 |
| HTTP + WebSocket 服务 | ⚠️ 协议复用、代码重写 | 协议帧设计不变，换成 Python socket 实现，约 200 行 |
| 配对码校验 / 单客户端互斥 / 防呆逻辑 | ✅ 逻辑复用 | 照搬设计即可 |
| 扫码配对流程 | ✅ 完全复用 | 前端 canvas 画码，不依赖电脑系统 |
| 注入引擎（SendInput） | ❌ 必须重写 | Win32 专属 API，麒麟上根本不存在 |
| 托盘 / 开机自启 / 日志 | ⚠️ 换实现 | 托盘走 AppIndicator，自启走 XDG autostart |
| 产品形态（只做管道、不做识别） | ✅ 理念不变 | 反而在 Linux 上更成立，因为它更松散 |

一句话，**Windows 版是"用 C# 调 Win32"，麒麟版是"用 Python 调 Linux 系统命令"**，是两份实现，共用一个手机端。

## 三、银河麒麟 V10 的真实环境（决定方案怎么选）

### 3.1 包管理与软件源

V10 **桌面版是 Debian/Ubuntu 系**，用的是 deb 包和 apt，源形如：

```
deb http://archive.kylinos.cn/kylin/KYLIN-ALL 10.0 main restricted universe multiverse
```

仓库分三层，base 放核心系统包，main 放官方认证应用，universe 放社区包。装第三方命令行工具，多半要从 universe 里来。

**一个容易踩的坑**：V10 服务器版 SP1/SP2 是 CentOS 系，用 yum；SP3 部分版本转向 Debian，用 apt。两派不能混用，不能用 `dpkg -i` 去装 rpm。我们面向桌面版，统一走 apt。

CPU 架构也要对上，常见 aarch64（飞腾、鲲鹏）、x86_64（兆芯、海光）、loongarch64（龙芯）。

### 3.2 桌面与显示协议

桌面是 UKUI，4.x 起 100% 用 Qt6 重写，窗口管理器是 **KWin**，也就是 KDE 那一套。

**V10 的会话类型各版本不一致，这是整份评估里最大的变量。** 有资料显示 V10 用 gdm3 驱动，默认走 Wayland；也有资料显示 UKUI 4.20 默认是 KWin-X11、并增强了 KWin-Wayland。同一个 SP 换个小版本都可能变。所以不能假设，只能现场验。

**好消息是有退路。** V10 可以修改 `/etc/gdm3/custom.conf`，把 `WaylandEnable=false` 取消注释，再重启 gdm3，就能把登录会话切回 X11。切回之后 xdotool 直接可用，整条链路就通了。这需要管理员权限，也会影响整机所有用户的会话，所以要不要动这台机器的配置，得先跟使用者或者单位的信息中心确认。

### 3.3 一条实测证据

有开发者公开记录过：在**银河麒麟 V10 SP1（2303）+ 飞腾 ARM64** 上，`sudo apt install xdotool` 能装上，`xdotool key a` 执行正常。这至少说明两件事，xdotool 在 V10 的源里有包、国产 ARM 芯片上有对应架构；这条路走得通，前提是那台机器处于 X11 会话。

### 3.4 动手之前，先跑检测脚本

`docs/check_kylin.sh`。拷到目标机器上执行：

```bash
bash check_kylin.sh
```

包含六项检测，系统与架构、显示会话、已装工具、uinput 权限、软件源可用性，以及最后一项**真实注入实测**。

前五项是纯只读，不会有任何副作用。第六项会真的往你打开的窗口里打一句中文，需要你确认后才执行。这一项是全部检测里最有价值的一条，因为它直接回答"这台机器到底能不能用"。

跑完脚本会自己给出推荐方案。把输出发回来，就能定下最终落地路径。

## 四、核心难点：Linux 的文本注入通道

这是整个评估里信息量最大的一块。Linux 没有 Windows 那种"合成键盘事件、系统自动转成 Unicode 字符"的一站式 API，得绕。

### 四种方案对比

| 方案 | 机制 | 能打中文吗 | X11 | GNOME Wayland | KDE/KWin Wayland | 权限要求 |
| --- | --- | --- | --- | --- | --- | --- |
| **xdotool** | X11 的 XTEST 扩展 | ✅ 能 | ✅ | ❌ | ❌ | 免权限 |
| **wtype** | virtual-keyboard-v1 协议 | ✅ 最好 | ❌ | ❌ | ❌ | 免权限 |
| **ydotool** | 内核 uinput | ❌ **打不出中文** | ✅ | ✅ | ✅ | 需 input 组 |
| **dotool** | uinput + XKB 布局 | ✅ 能 | ✅ | ✅ | ✅ | 需 input 组 |
| **eitype** | libei / EI 协议 | ✅ 全 Unicode | ❌ | ✅ GNOME 46+ | ✅ Plasma 6.1+ | 需 Rust 编译 |
| **剪贴板粘贴** | wl-copy 写剪贴板 + 模拟 Ctrl+V | ✅ 能 | ✅ | ✅ | ✅ | 免权限（模拟按键那步除外） |

### 三个必须先知道的坑

**坑一，ydotool 打不出中文。** 它只发送美式键盘的原始键码，中文没有对应键码。网上很多教程推荐 ydotool，但它实际上只能用来模拟快捷键（比如 Ctrl+V），不能用来"打字"。这一条直接决定中文场景不能用它做主通道。

**坑二，wtype 在麒麟上大概率不可用。** wtype 依赖 compositor 实现 virtual-keyboard-v1 协议，而 **KDE 的 KWin 和 GNOME 的 Mutter 都没有实现这个协议**。麒麟 UKUI 用的正是 KWin，所以这条路基本堵死，除非现场实测打脸。

**坑三，xdotool 只在 X11 下有效。** 它走 X11 的 XTEST 扩展，Wayland 出于安全设计禁止客户端伪造输入事件，所以 Wayland 下完全失效。

### 麒麟上的推荐优先级

1. **如果检测出来是 X11** → 直接用 `xdotool type`，这是最省事、中文原生支持、还不用权限的一条路。
2. **如果检测出来是 Wayland** → 走**剪贴板方案**：把文字写进剪贴板（wl-clipboard 的 wl-copy），再模拟一次粘贴快捷键。这是唯一在所有桌面环境都被验证可行、且中文绝对不出错的路。代价是两条，会覆盖用户当前剪贴板（可以做成用完自动还原），以及终端里粘贴是 Ctrl+Shift+V 不是 Ctrl+V（做成可配置）。
3. **如果 uinput 可用且有 input 组权限** → 上 `dotool` 作为体验升级，它能真正"打字"而不占用剪贴板，中文也支持。

## 六、风险清单（按严重程度排）

1. **显示协议不确定（最高）**。同一款麒麟换个 SP 版本就可能从 X11 变 Wayland，方案要能自适应，不能写死。所以必须做"运行时检测 + 多通道可切换"。
2. **中文注入受限**。不能用 ydotool 打字，只能走剪贴板或 dotool。剪贴板方案的副作用要提前跟使用者说清楚。
3. **权限与信创环境的管控**。uinput 方案要 input 组，政企环境里 sudo 常常收得很紧；麒麟还有 kysec 强制访问控制，会不会拦模拟输入需要现场验证。
4. **CPU 架构差异**。飞腾、鲲鹏是 ARM64，龙芯是 LoongArch。第三方命令行工具的包在非 x86 架构上是否有，要逐个确认。纯 Python 加系统命令的方案适配成本最低。
5. **合规问题**。单位电脑上装未经认证的软件本身可能违规，分发得走内网或者走申请流程。这一条不是技术问题，但常常是真正的拦路虎。
6. **终端粘贴快捷键不同**。剪贴板方案要允许自定义粘贴组合键。

## 九、总体判断

麒麟版属于"**能做，但必须先确认现场环境**"的项目。代码层面没有拦路虎，真正的变量是显示协议、权限管控和单位的分发政策。

只要第一步的现场检测能确认注入通道走得通，后面就是两三天的事。如果检测发现机器是 Wayland 加严格权限管控，那就要跟使用者摊开讲清楚，剪贴板方案能覆盖 95% 的场景，但它不是无痕的。
