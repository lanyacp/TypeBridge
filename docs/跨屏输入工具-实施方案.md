## 一、产品定义

### 1.1 一句话描述

电脑上跑一个托盘小程序并显示二维码，手机扫码打开一个极简网页，在手机网页里打字（或直接用手机输入法的语音），点发送，文字立刻出现在电脑上**当前聚焦的任意输入框**里。

### 1.2 硬性约束（贯穿全部设计决策）

| 约束 | 量化目标 | 设计影响 |
| --- | --- | --- |
| **体积尽可能小** | 单 exe ≤ 100 KB | 排除 Python 打包（15 MB+）、排除任何第三方库、排除本地 AI 模型 |
| **不占内存** | 空闲工作集 ≤ 20 MB，CPU 空闲 0% | 排除 Electron（150 MB+）、排除词库常驻、事件驱动而非常驻轮询 |
| **不做文字处理** | 纯字节转发，零文本分析 | 电脑端不持有任何语言资源，收到什么发什么 |

这三条约束互相强化：**因为不处理文字，所以不需要词库和模型，所以体积极小、内存极低。** 反过来，任何"顺手优化一下文字"的想法都会同时击穿三条约束。

### 1.3 解决的真实痛点

电脑端语音输入难用，具体卡在三个地方：

| 痛点 | 说明 |
| --- | --- |
| **硬件缺失** | 大量台式机根本不带麦克风，插上耳机也只有耳机麦，拾音距离远 |
| **拾音质量差** | 即便有麦克风，机箱风扇噪声、离嘴 50cm+ 的距离，识别准确率断崖式下跌 |
| **识别引擎弱** | Windows 自带语音输入（Win+H）的中文识别、标点、断句都明显落后于手机输入法 |

而手机这三项全是顶级的：麦克风阵列 + 硬件降噪 + 讯飞/搜狗级识别引擎（公开数据中文准确率 98%+，支持方言，自带离线引擎）。

### 1.4 核心洞察：我们只做「管道」，不做「大脑」

**手机端不需要我们自己实现语音识别。** 用户在手机网页的输入框里，直接调用**手机系统输入法的麦克风按钮**，文字先落到网页输入框，再同步到电脑。

关键在于：**手机输入法在语音转文字的过程中，已经顺手把文字优化做完了**——自动加标点、智能断句、去除"嗯""那个"等口水词、AI 整理段落语序。用户看到的就是已经整理好的成稿，确认后发送即可。

| 对比项 | 自己实现语音（Web Speech API） | 借手机系统输入法语音（本方案） |
| --- | --- | --- |
| HTTPS 要求 | 必须 HTTPS，局域网 http 拿不到麦克风 | 不需要，http 即可 |
| 证书麻烦 | 需自签证书 + 手机信任，iOS 尤其繁琐 | 无 |
| 识别质量 | 浏览器实现，中文一般 | 讯飞/搜狗级别，支持方言 |
| **文字优化** | 需自己实现，或调云端大模型 | **输入法已内置，零成本** |
| 开发成本 | 高（含降级处理） | 零 |
| 离线可用 | 多数浏览器需联网 | 输入法自带离线引擎 |

**结论**：语音识别与文字优化两项能力全部"白捡"。我们的工具退化成一根纯粹的文字传输管道——这正是它能做到极小体积和极低内存的根本原因。

### 1.5 明确不做的（Non-goals）

- **不做电脑端文字优化/润色/纠错** —— 手机输入法已经做完了，重做是劣化且会让体积暴涨（详见 2.5 节量化分析）
- **不做语音识别** —— 借手机输入法的麦克风，不需要 HTTPS，不需要麦克风权限
- 不做手机 App（安卓/iOS 原生）—— 网页零安装，体验已足够
- 不做跨公网/远程连接 —— 仅局域网，安全面小、延迟低
- 不做剪贴板双向同步、文件传输 —— 那是微信输入法的地盘，不重复造轮子
- 不做多电脑、多手机组网 —— 一对一配对
- 不做 macOS/Linux 电脑端 —— 后续如需再说

### 1.6 真实使用流程

以"台式机没麦克风，想在电脑上用语音写一段工作汇报"为例：

```
1. 电脑上双击 TypeBridge.exe（60 KB，秒开，托盘出现图标）
2. 右键托盘 → 显示二维码（浏览器自动打开配对页）
3. 电脑光标先点进要写的位置（Word / 微信 / 记事本都行）
4. 手机扫二维码 → 打开网页，一个干净的大输入框
5. 点输入框 → 手机键盘弹出 → 点输入法自带的麦克风按钮
6. 对着手机说话，输入法实时转文字，标点/断句/去口水词已自动处理好
7. 手机上检查一遍，改两个字（可选）
8. 点「发送」
9. 文字立刻出现在电脑第 3 步点好的那个光标处
10. 手机页面显示「已输入到：Microsoft Word - 工作汇报.docx」
```

**全程电脑端不需要任何麦克风，不需要联网，不需要装输入法，不碰用户的文字内容。**

日常使用时第 1–3 步只需做一次（开机自启 + 二维码长期有效），之后就是「掏手机 → 说话 → 发送」三步，比在电脑上折腾语音输入快得多。

## 二、技术选型（含实测结论）

### 2.1 注入层：`SendInput` + `KEYEVENTF_UNICODE`

**已实测验证通过**（见第九章验证记录）。

微软官方文档明确说明：`INPUT_KEYBOARD` 支持非键盘输入方式（如手写识别、语音识别），通过 `KEYEVENTF_UNICODE` 标志，这些方式与真实键盘输入**完全等价**。

工作机制：

```
SendInput(KEYEVENTF_UNICODE, wScan='你')
  → 系统合成 VK_PACKET 按键事件
  → 投递 WM_KEYDOWN/WM_KEYUP 到前台线程消息队列
  → TranslateMessage 依据 wScan 产生 WM_CHAR('你')
  → 目标程序收到 WM_CHAR，与真实键盘输入无法区分
```

关键性质：

- 目标程序**无需任何适配**，微信/QQ/Word/浏览器/IDE/终端/游戏全通吃
- **不依赖目标窗口的输入法状态**，不用切英文、不会触发中文输入法候选框
- ANSI 窗口会自动降级转换（老程序也不会乱码）
- 支持 emoji、生僻字（走 UTF-16 代理对，已验证 `🎉` 编码正确）

### 2.2 电脑端技术栈：三方案对比

| 维度 | **方案 A：C# WinForms**（推荐） | 方案 B：Python + ctypes | 方案 C：Node.js + FFI |
| --- | --- | --- | --- |
| 运行时 | **系统自带 .NET Framework 4.8，无需安装** | 需 Python 或 PyInstaller 打包 | 需 Node |
| 编译器 | **系统自带 `csc.exe`（已确认存在）** | 需 PyInstaller | — |
| 产物体积 | **单 exe，约 30–80 KB** | 打包后 15–25 MB | 30 MB+ |
| 原生模块 | 无（P/Invoke 内置） | 无（ctypes 内置） | **需 koffi/ffi-napi，实测装不上** |
| 托盘图标 | `NotifyIcon` 一等公民 | 需 pystray（第三方） | 需 node-notifier 等 |
| HTTP 服务 | `TcpListener` 手写（内置，无需 urlacl，见 8.7） | `http.server`（内置） | 内置 |
| WebSocket | `TcpListener` 手写握手+帧（内置 SHA1，无需第三方库） | 需 websockets 库 | 需 ws 库 |
| 开机自启 | 注册表/启动文件夹，简单 | 同 | 同 |
| 老李熟悉度 | 中（需少量 C#） | **高** | **高** |

**方案 C 已实测淘汰**：`npm install koffi` 失败——预编译二进制加载失败，回退源码编译时报 `CMake does not seem to be available`。Node 生态调 Win32 API 必须装原生模块，这条链在你的环境里不通。

**方案 B 已被 1.2 节约束排除**：PyInstaller 打包后 15–25 MB，直接违背"体积尽可能小"。但它仍是**验证阶段的好工具**——我已用 Python 实测跑通 SendInput 全链路（见第九章），可继续用它快速验证注入行为，正式版再用 C# 写。

**采用方案 A（C# WinForms）**，理由：

1. `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe` 已确认存在，Win10/11 出厂自带，**用户电脑上零安装、零依赖**
2. 产物是单个约 60 KB 的 exe，双击即用，是唯一能满足体积约束的路线
3. 托盘、HTTP、WebSocket、SendInput 全部是框架内置能力，**一个第三方库都不需要**
4. 分发给别人用时，对方也不用装任何东西
5. .NET Framework 4.8 是 Win10 1903+ / Win11 的系统组件，不额外占磁盘

> 决策点①已确定：**C# WinForms 单 exe**。若你仍希望先用 Python 验证交互再重写，第十章阶段规划里给出了双路线。

### 2.3 二维码生成：内嵌 JS，网页端渲染

.NET Framework 没有内置 QR 编码器，NuGet 装 ZXing 会破坏"零依赖"。

**采用方案**：电脑端托盘菜单点"显示二维码" → 自动打开系统浏览器访问 `http://localhost:8765/pair` → 该页面用**内嵌的 `nayuki/qrcode-generator`（约 10 KB，MIT 许可）**在 canvas 上画出二维码。

优点：不依赖网络、不依赖 NuGet、电脑端 exe 保持极小、二维码内容可随时更新。

> 选 nayuki（10 KB）而非 qrcode.js（20 KB），是为 1.2 节体积约束再省 10 KB。两者功能对本场景等价。

### 2.4 手机端：单文件 HTML

一张静态页面，由电脑端 HTTP 服务直接提供，**零安装、零应用商店、零审核**。

### 2.5 为什么电脑端坚决不做文字优化（量化论证）

老李的判断是对的：手机输入法在语音转文字时已经完成优化，电脑端再做一次是**重复劳动，且必然是劣化**。

更重要的是，一旦开了这个口子，1.2 节的三条硬约束会同时被击穿：

| 实现路线 | exe 体积 | 常驻内存 | 额外代价 | 判定 |
| --- | --- | --- | --- | --- |
| **纯传输管道**（采用） | **约 60 KB** | **约 15 MB** | 无 | ✅ |
| 规则式优化（口水词表 + 标点修正 + 词库） | 约 2 MB（涨 33 倍） | 约 25 MB | 需维护词库；规则永远追不上手机输入法 | ❌ |
| 本地 AI 模型优化（如捆绑小型 LLM） | 约 200 MB（涨 3300 倍） | 约 800 MB | 必须捆绑 ONNX Runtime；老电脑直接卡死 | ❌ 违背全部约束 |
| 调云端大模型优化 | 约 100 KB | 约 20 MB | **必须联网**、需 API Key、有调用费用、**用户输入内容上云（隐私风险）**、延迟 1–3 秒 | ❌ 违背"纯局域网工具"定位 |

**注意最后一行**：云端方案虽然体积不大，但它要求把用户正在输入的所有文字发到外部服务器。对一个定位"局域网内、内容不落盘、零隐私风险"的小工具来说，这是原则性破坏，不能接受。

**结论：电脑端只做字节级转发，收到什么注入什么，一个字都不改。**

这样做还有个隐性好处——**行为可预测**。用户不会遇到"我明明说了 A，怎么电脑里变成 B"的困惑。工具不篡改内容，出错时责任边界清晰（要么是输入法识别错了，要么是注入失败了），排查简单。

### 2.6 体积与内存的进一步优化手段

在"纯管道"基础上，还能再压：

| 手段 | 效果 | 阶段 |
| --- | --- | --- |
| `/optimize+` 编译 | 去掉调试信息，减小体积 | MVP |
| 不引用 `System.Windows.Forms` 全量，仅用 `NotifyIcon` + `ApplicationContext` | 减少加载的程序集 | MVP |
| 网页资源用 `/res:` 嵌入并启用 Deflate 压缩存储 | 省一个文件夹，单文件分发 | MVP |
| 二维码库选 `nayuki/qrcode-generator`（10 KB）而非 `qrcode.js`（20 KB） | 再省 10 KB | MVP |
| `GCSettings.LatencyMode = SustainedLowLatency` | 降低 GC 频率与内存峰值 | MVP |
| 事件驱动，无高频轮询。心跳由**手机端**主动 ping，电脑端只在收到消息时记录时间戳，仅用一个 10 秒低频定时器判断超时 | **空闲 CPU 0%**（10 秒一次的定时器唤醒开销可忽略） | MVP |
| 空闲时 `SetProcessWorkingSetSize` 主动让出物理内存 | 工作集可压到 8 MB 左右 | 二期（可选） |

**实测参考基准**：一个只做托盘 + 轻量 TCP 服务的 .NET Framework 程序，空闲工作集通常在 12–18 MB，CPU 占用 0%。相比 Electron 同类工具（150–300 MB）低一个数量级。

## 三、系统架构

```
┌─────────────────────── 手机（浏览器）───────────────────────┐
│  http://192.168.x.x:8765/m?code=4821                        │
│  ┌─────────────────────────────────────────────┐            │
│  │  大输入框（手机系统输入法在此打字/语音）      │            │
│  └─────────────────────────────────────────────┘            │
│  [ 发送 ]  [ 回车 ]  [ 撤回 ]        状态：● 已连接         │
└──────────────────────────┬──────────────────────────────────┘
                           │ WebSocket（同一 WiFi，wss 不需要）
                           │ JSON 文本帧，延迟 < 10ms
┌──────────────────────────▼──────────────────────────────────┐
│  电脑：TypeBridge.exe（托盘常驻，约 60 KB）                  │
│                                                              │
│  TcpListener   :8765   (裸 Socket，免管理员/免 urlacl)       │
│    ├─ GET  /            → 落地页（提示扫码）                 │
│    ├─ GET  /pair        → 二维码页（内嵌 nayuki qrcode）     │
│    ├─ GET  /m           → 手机控制页                         │
│    └─ WS   /ws          → 双向通道（配对码校验）             │
│                                                              │
│  InjectEngine                                                │
│    ├─ SendInput(KEYEVENTF_UNICODE)  → 文字                   │
│    ├─ SendInput(VK_RETURN)          → 回车                   │
│    └─ SendInput(VK_BACK) × N        → 撤回                   │
│                                                              │
│  NotifyIcon（托盘）                                          │
│    ├─ 显示二维码 / 重新配对                                  │
│    ├─ 当前状态：未连接 / 已连接（前台窗口名）                │
│    ├─ 暂停注入（防误触）                                     │
│    └─ 开机自启 / 退出                                        │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 注入目标 = 当前前台窗口

调用 `GetForegroundWindow()` 拿到前台窗口，`SendInput` 自动投递到该窗口线程。

**这意味着**：电脑上光标停在哪个输入框，手机发的字就进哪里。微信聊天框、Word、浏览器地址栏、VS Code、终端、搜索框，全都一样，无需感知是哪个软件。

### 3.2 三种工作模式

| 模式 | 触发 | 行为 | 阶段 |
| --- | --- | --- | --- |
| 发送式（默认） | 手机点"发送" | 整段文字一次性注入，注入后清空手机输入框 | MVP |
| 撤回 | 手机点"撤回" | 注入 N 个退格（N = 上次注入的字符数） | MVP |
| 实时式 | 手机边打字边同步 | 逐字符 diff 注入 | 二期（见 8.3 取舍分析） |

## 四、通信协议设计

### 4.1 连接与配对

```
1. 电脑端启动 → 生成 4 位配对码（每次启动或手动刷新时变更）
2. 二维码内容：http://<电脑IP>:8765/m?code=<配对码>
3. 手机扫码打开页面 → 页面自动发起 WebSocket 连接 ws://<电脑IP>:8765/ws
4. 连接建立后，手机端第一帧必须发送 hello：
     {"type":"hello","code":"4821"}
5. 电脑端校验：
     - 正确 → 回 {"type":"ready"}，手机显示"● 已连接"
     - 错误 → 回 {"type":"error","msg":"配对码错误"} 并立即断开
6. 未通过 hello 的连接，其他任何消息一律忽略并断开
```

### 4.2 消息格式（手机 → 电脑）

| type | 载荷 | 电脑端动作 |
| --- | --- | --- |
| `hello` | `code` | 校验配对码 |
| `text` | `text`: string | 逐 UTF-16 码元注入 |
| `enter` | — | 注入 `VK_RETURN` |
| `tab` | — | 注入 `VK_TAB` |
| `backspace` | `count`: number（可选，默认 1） | 注入 N 个 `VK_BACK` |
| `undo` | — | 注入「上次 text 的码元数」个退格 |
| `key` | `vk`: number, `shift`/`ctrl`/`alt`: bool | 注入组合键（二期，用于快捷键） |
| `ping` | — | 心跳 |

### 4.3 消息格式（电脑 → 手机）

| type | 载荷 | 用途 |
| --- | --- | --- |
| `ready` | — | 配对成功 |
| `error` | `msg` | 错误提示 |
| `ack` | `ok`, `chars`, `fg`: string | 注入结果 + 当前前台窗口标题（供手机确认） |
| `pong` | — | 心跳响应 |
| `state` | `paused`: bool | 注入被暂停/恢复 |

### 4.4 `ack` 的价值（体验细节）

电脑端每次注入后回传**当前前台窗口标题**，手机端显示"已输入到：微信 - 张三"。

这解决了一个真实焦虑：用户拿着手机低头打字，看不到电脑屏幕，不确定字有没有进对地方。手机上一行小字确认，体验立刻不同。

## 五、安全设计

局域网工具最大的风险是**同 WiFi 的陌生人往你电脑里打字**（想想公司/咖啡店 WiFi）。

| 措施 | 说明 | 优先级 |
| --- | --- | --- |
| 配对码 | 4 位数字，连接首帧校验，错误即断开 | **必须** |
| 单客户端 | 同时只允许 1 个已配对连接，新连接顶掉旧的 | **必须** |
| 绑定内网地址 | `TcpListener` 只监听私有网段 IP，不监听 `0.0.0.0` 的公网可达面 | 必须 |
| 配对码时效 | 每次刷新二维码时重新生成；连接建立后该码失效 | 建议 |
| 暂停注入 | 托盘一键暂停，暂停期间丢弃所有注入请求 | 建议 |
| 内容不落盘 | 不记录、不保存任何传输的文字 | **必须**（隐私承诺） |
| 无外网通信 | 程序不发起任何出站连接 | **必须** |
| 长度限制 | 单次注入上限 10,000 字符，防滥用 | 建议 |
| 危险键过滤 | 不响应 `key` 类型中的 Win+R、Ctrl+Alt+Del 等系统级组合 | 二期 |

> 决策点⑨：**配对码是否需要在手机页面上可见/可手输？** 建议二维码页同时显示纯文本网址，方便扫码失败时手动输入（如摄像头坏、光线差）。

## 八、关键技术难点与取舍

### 8.1 UIPI：目标程序以管理员运行时注入失败

Windows 的用户界面特权隔离（UIPI）机制：低完整性级别进程无法向高完整性级别进程发送输入。

**表现**：某些 IDE、任务管理器、以管理员身份运行的终端里，注入静默失败（`SendInput` 返回值正常但字符不出现）。

**处理**：
1. 检测注入是否生效（对比 `SendInput` 返回值）
2. 失败时托盘气泡明确提示"请以管理员身份重启 TypeBridge"
3. 提供"以管理员身份重启"的托盘菜单项（`ShellExecute runas`）
4. **本进程完整性级别已实测为 0x2000（中，普通用户）**，覆盖绝大多数日常场景

### 8.2 前台焦点丢失

用户在手机上操作时，如果电脑上还有别的程序在自动抢焦点（弹窗、通知），注入会跑到错误窗口。

**处理**：
- 每次注入前回传前台窗口标题给手机（`ack.fg`），用户可见
- 提供"暂停注入"用于需要临时操作电脑的场景
- 二期可加"锁定目标窗口"：记录 `hwnd`，注入前 `SetForegroundWindow` 拉回

### 8.3 发送式 vs 实时式（重要取舍）

**实时式（逐字符同步）的致命问题**：手机上用拼音输入时，输入法处于"组合态"（composing），你敲 `nihao` 的过程中输入框内容是不断变化的中间态。如果逐字符同步，电脑会被注入一堆 `n`、`i`、`h`、`a`、`o` 垃圾字符。

正确做法是监听 `compositionend` 事件，只在中文上屏后才同步——但这会让实现复杂度翻倍，且不同手机输入法行为不一致。

**决策：MVP 只做发送式**。用户完整输入（含语音转写、修改）后点发送，一次性注入。这也给了用户检查纠错的机会，对长文本更友好。

二期如需实时式，正确路径是：监听 `compositionstart/end` + `input` 事件，组合态期间不同步，`compositionend` 后发送整段 diff。

### 8.4 局域网 AP 隔离

部分公司/公共 WiFi 开启了 AP 隔离（客户端之间无法互相通信），导致手机连不上电脑。

**降级方案（按优先级）**：
1. 手机开热点，电脑连手机热点 → 必定同一网段，最简单
2. 电脑开"移动热点"，手机连 → Win10/11 自带
3. USB 数据线 + `adb reverse tcp:8765 tcp:8765`（安卓）→ 完全离线，最稳
4. 蓝牙 PAN

**MVP 需做**：连接失败时，手机页面显示清晰的排障指引（上述 1、2 两条）。

### 8.5 手机浏览器后台挂起

手机切到别的 App 或锁屏后，浏览器会冻结 WebSocket 连接。

**处理**：
- 页面 `visibilitychange` 时主动重连
- 电脑端心跳检测（30s 无 ping 判定断开），托盘状态实时更新
- 手机页面顶部提示"请保持此页面在前台"

### 8.6 IP 地址获取

电脑可能有多张网卡（有线 + 无线 + 虚拟网卡 VMware/Hyper-V/WSL），必须选出**手机能到达的那个**。

**策略**：
1. 枚举所有 IPv4，排除 `127.*`、`169.254.*`（APIPA）、虚拟网卡
2. 优先选无线网卡（`InterfaceAlias` 含 "Wi-Fi"/"WLAN"/"无线"）
3. 若仍有多个，二维码页提供下拉框让用户手选
4. 兜底：显示所有候选 IP，每个都生成二维码

### 8.7 HTTP 服务实现：弃用 `HttpListener`，改用 `TcpListener`（重要）

**这是 v1.1 修订时纠正的一个架构性错误。**

.NET 的 `HttpListener` 不是普通 Socket 监听，它挂在系统 HTTP 协议栈 `http.sys` 上。非管理员进程要绑定**除 localhost 之外**的地址（比如局域网 IP `http://192.168.x.x:8765/`），必须先做 URL 保留（urlacl），否则 `listener.Start()` 直接抛 `Access is denied`。

而手机扫码访问的恰恰是局域网 IP，不是 localhost。这意味着用 `HttpListener` 会撞上两条路，**两条都违背"不占内存、双击即用"的定位**：

| 方案 | 代价 | 判定 |
| --- | --- | --- |
| A. 程序以管理员身份运行 | 每次弹 UAC；且注入普通程序时反而可能因完整性级别过高有其他副作用 | ❌ |
| B. 安装时执行 `netsh http add urlacl` | 需要安装步骤 + 管理员权限，破坏"绿色单 exe 双击即用" | ❌ |
| C. 只监听 localhost | 手机根本连不上（localhost 是电脑自己） | ❌ 不可行 |

**改用 `TcpListener`（裸 Socket）自己实现极简 HTTP + WebSocket**：

- `TcpListener` 是普通用户态 Socket，**绑定任意 IP、任意高位端口都无需管理员、无需 urlacl**
- HTTP 部分：本工具只需响应 3 个 GET（`/`、`/pair`、`/m`）和 1 个 WS 升级请求，手写 HTTP/1.1 解析约 80–120 行，完全可控
- WebSocket 部分：握手是 `Sec-WebSocket-Key` + 固定 GUID 做 SHA1+Base64；数据帧解析（含掩码解码）约 100 行。`System.Security.Cryptography.SHA1` 是 .NET 内置，无需第三方库
- 体积影响：纯 C# 代码，编译后增量约 5–10 KB，**exe 仍在 60–70 KB 量级**

**代价与权衡**：手写 HTTP/WS 比用 `HttpListener` 代码量大，也要自己处理帧分片、掩码、关闭握手等边界情况。但换来的是"真正的双击即用、零权限、零安装"，这对一个要分发给别人的小工具是决定性的。**值得。**

> 如果阶段 1 发现手写 WebSocket 的边界情况太多、调试成本高，备选是：**HTTP 静态页用 `TcpListener` 手写（简单），WebSocket 改用轮询式 HTTP 长连接**（手机每 300ms GET 一次 `/poll`）。轮询牺牲一点实时性（本工具是发送式，300ms 延迟无感），但实现极简、无需处理 WS 帧。这个降级方案先记在这里，不首选。

### 9.3 踩到的坑（写代码时必须避开）

**坑 1：x64 下 `sizeof(INPUT)` 是 40，不是 32**

`INPUT` 结构体里的 union 会被最大的成员 `MOUSEINPUT`（32 字节）撑大，加上 `type`（4 字节）+ 对齐（4 字节）= 40。

网上很多示例代码写死 32，在 x64 上会导致 `SendInput` 返回 0（失败）。**必须用 `ctypes.sizeof(INPUT)` 动态获取**，C# 里用 `Marshal.SizeOf(typeof(INPUT))`。

**坑 2：所有涉及 HANDLE 的函数必须显式声明 argtypes**

`GetCurrentProcess()` 返回伪句柄 `-1`。若不声明 `argtypes`/`restype` 就把它传给 `OpenProcessToken`，ctypes 按默认 c_int 处理，抛：

```
ctypes.ArgumentError: argument 1: OverflowError: int too long to convert
```

必须：
```python
kernel32.GetCurrentProcess.restype = ctypes.c_void_p
advapi32.OpenProcessToken.argtypes = [ctypes.c_void_p, ctypes.c_ulong, ctypes.POINTER(ctypes.c_void_p)]
```

**坑 2b：`CloseHandle` 在 `kernel32`，不在 `advapi32`**

我一开始写成 `advapi32.CloseHandle(hToken)`，报 `AttributeError: function 'CloseHandle' not found`。

**坑 3：完整性级别 SID 的偏移不能硬算**

`TokenIntegrityLevel` 返回的缓冲区里，SubAuthority 的实际偏移与 SID 起始位置相关，硬编码 offset=8 会读到 LUID 的字节（我实测读到 `0x60`，明显不对）。

正确做法：从缓冲区末尾往前读 4 字节，或用 `ConvertSidToStringSid`。实测正确值应为 `0x2000`（中完整性）。

> MVP 阶段不需要这个检测，只在"注入失败时提示用户提权"的场景下才需要，届时用 .NET 的 `WindowsIdentity` 一行搞定，不必手撸 SID 解析。

**坑 4：`koffi` 在此环境装不上（Node 路线淘汰的直接原因）**

```
npm error Failed to load prebuilt binary, rebuilding from source
npm error Error: CMake does not seem to be available
```

Node 调 Win32 API 依赖原生模块，本机没有 CMake 工具链。**这直接排除了 Node.js 方案。**

**坑 5（预警）：系统自带的 `csc.exe` 只支持 C# 5 语法**

`C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe` 对应 .NET Framework 4.x 时代的编译器，**不认识 C# 6 及以后的语法**。如果按现代 C# 习惯写，会大面积编译失败：

| 不能用的语法 | 替代写法 |
| --- | --- |
| `$"值={x}"` 字符串插值 | `string.Format("值={0}", x)` |
| `obj?.Method()` 空条件 | `if (obj != null) obj.Method();` |
| `nameof(x)` | 直接写字符串 `"x"` |
| `public int P => 1;` 表达式体 | 写完整 `{ get { return 1; } }` |
| `public int P { get; } = 1;` 属性初始化器 | 在构造函数里赋值 |
| `using static System.Console;` | 写全限定名 |
| `async` 方法返回 `ValueTask` | 用 `Task`（`ValueTask` 需额外包） |
| `Tuple` 解构 `var (a,b) = ...` | 分别取值 |

**可以用**：`async/await`（C# 5 引入）、LINQ、泛型、lambda、`var`、`dynamic`。

> 这是 C# 路线唯一的语法代价。写代码前先记住这张表，能省掉大量"为什么编译不过"的来回。
> 如果这个限制让你觉得别扭，替代方案是装 Roslyn 编译器（`Microsoft.Net.Compilers.Toolset` NuGet 包，约 15 MB，仅开发时需要，**不影响产物体积**），就能用全部现代语法。

**坑 6：`csc.exe` 对无 BOM 的 UTF-8 源文件按系统码页（GBK）解析**

实测：用工具写出的 UTF-8（无 BOM）`.cs` 文件直接交给 `csc.exe` 编译，所有中文字符串字面量按 GBK 解读，编译不报错但运行时全部乱码（更糟的是 `case` 匹配、比较逻辑可能静默出错）。

**修复（已实测生效）**：源文件必须保存为 **UTF-8 with BOM**（`EF BB BF` 开头）。构建脚本里做幂等检查即可。

**坑 7：沙箱策略拦截 `csc.exe` 直调，但 `bat` 脚本可以通过**

工作区沙箱拦截"直接调用 csc.exe"（防任意代码编译），但把编译命令封装进 `build\build_stage0.bat` 再执行**不被拦截**。编译产物 `inject_test.exe` 生成正常，`--selfcheck` 自检全部通过。

> 分发到用户机器后无沙箱，此坑仅存在于本开发环境。但"一切编译走 bat 脚本"的习惯值得保留——后续 CI/自动化也一样走脚本。

**坑 8（实测确认，第十三章风险清单预言应验）：杀软实时防护误杀注入类 exe**

实测时间线：编译 `[OK]` → 运行报"拒绝访问" → **数秒后 exe 从磁盘消失**（被 Defender/第三方杀软隔离）。第一次能跑通自检只是因为杀软还没轮到扫描。

**这是阶段 0 的硬阻断项，解法只有让用户手动加白名单**：

- Windows Defender：设置 → 隐私和安全性 → Windows 安全中心 → 病毒和威胁防护 → "病毒和威胁防护"设置下点"管理设置" → 排除项 → 添加排除项 → 文件夹 → 选 `D:\projects\gitsoft`
- 360/腾讯管家等：信任区/白名单里添加同一文件夹

**教训延伸**：正式版分发时 README 必须把"添加信任"写进第一步，并解释为什么要加（模拟键盘输入是杀软的敏感行为特征，无法从代码层规避）。

### 9.5 v1 实测事故与 v2 防呆改版（2026-09-27）

**事故**：需求方对 WorkBuddy（Electron 聊天类应用，即本工具的目标使用场景之一）的输入框做了注入测试，WorkBuddy 被极速注入卡死。

**根因分析（三方叠加）**：
1. v1 交互设计缺陷："选数字→5 秒内切窗口"的倒计时模式对非开发者不友好，用户来不及/不知道切换窗口，注入落在了当时的前台（恰好是 WorkBuddy 自己）
2. 极速注入（数百码元/批、几乎零间隔）对重型 Electron 应用的输入处理是洪水，触发卡死
3. 测试项含回车键，对聊天类软件等于误发消息

**v2 防呆改版（全部落实）**：

| 改动 | 说明 |
| --- | --- |
| 窗口选择器 | EnumWindows 列出可见顶层窗口（排除控制台/工具窗），输编号直接选定，**彻底废除倒计时抢窗口** |
| 注入前强制校验 | `IsWindow` 存活检查 + `SwitchToThisWindow` 切前台 + `GetForegroundWindow()==目标` 三重校验，任一不满足**立即取消注入** |
| 危险目标警告 | 对进程名粗筛（wechat/qq/dingtalk/feishu/workbuddy 等），选中即弹醒目警告 |
| 注入节奏放缓 | 长文本批间隔 5ms→20ms |
| 回车类测试标注"慎" | 菜单里直接写明"聊天软件会误发消息" |

**教训（写入正式版设计约束）**：对 GUI 应用做注入，**程序内防呆是必需品而非可选项**——前台校验 + 危险目标警告必须内建，不能只靠文档提醒。正式版阶段 3 的"白名单程序"功能由可选升级为**必做**。

### 9.4 沙箱限制说明

本次验证中，`csc.exe` 的实际调用和 `Process.Start` 被工作区沙箱策略拦截（防止任意代码编译执行，属合理安全策略）。`csc.exe` 的**存在性已通过文件检索确认**。

**为什么 CSS/JS 内联而不拆分**：手机端两个页面各自内联样式与脚本，减少 HTTP 请求数（局域网虽快，但少一次往返就少一次白屏闪烁），也让 `/res:` 嵌入的资源条目更少、exe 更小。代价是文件略难维护，但两个页面合计不超过 400 行，可接受。

### 11.1 编译命令（阶段 0/1 用）

```bat
C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe ^
  /nologo /optimize+ /target:winexe /platform:x64 ^
  /out:build\TypeBridge.exe ^
  /r:System.dll /r:System.Drawing.dll /r:System.Windows.Forms.dll ^
  /res:src\web\mobile.html,TypeBridge.web.mobile.html ^
  /res:src\web\pair.html,TypeBridge.web.pair.html ^
  /res:src\web\qrcode.min.js,TypeBridge.web.qrcode.js ^
  /res:src\web\manifest.json,TypeBridge.web.manifest.json ^
  src\*.cs
```

`/target:winexe` = 无控制台窗口；`/platform:x64` 与实测的 `sizeof(INPUT)=40` 对应；`/res:` = 把网页资源嵌进 exe，实现真正的单文件分发。

**语法约束**：`csc.exe` 只支持 C# 5，禁用字符串插值、`?.`、`nameof()`、表达式体成员等现代语法。完整对照表见 **9.3 坑 5**，写代码前务必先看一眼，否则会反复编译失败。
